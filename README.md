# Secure 2-Tier AWS Infrastructure

A production-style infrastructure platform for a voting application — built with security enforcement at every layer, not bolted on at the end.

## Why this exists

Most infrastructure projects treat security as a final checklist. This one treats it as a constraint that shapes every decision from the first line of Terraform. The goal was to build something where a misconfigured resource physically cannot reach production — not because someone reviewed it, but because the pipeline won't allow it.

---

## Architecture

**Traffic flow:**
```
Internet → ALB (public subnet) → EC2 x2 (private subnet, 2 AZs) → RDS (private subnet)
```

No component has more network access than it needs to do its job.

- ALB lives in public subnets across two AZs and is the only ingress point
- Two EC2 instances run in private subnets — one per AZ — behind an Auto Scaling Group. If one AZ goes down, the other instance keeps serving traffic
- RDS security group allows inbound on port 3306 from the EC2 security group ID only — not from a CIDR range, because CIDR-based rules break silently when instances scale or IP addresses change
- Secrets Manager is accessed via IAM role on the EC2 instance — no access keys, no environment variable injection of credentials
- NAT Gateway provides outbound internet access for private subnet instances without exposing them to inbound traffic

---

## Security decisions

### Secrets management

Database credentials live in AWS Secrets Manager only, encrypted with a Customer-Managed KMS Key (CMK). The CMK provides a second independent access control layer — even if an IAM policy is misconfigured, the CMK resource policy restricts which roles can decrypt. AWS-managed keys do not offer this.

Credentials are generated by Terraform's `random_password` resource at apply time and written directly to Secrets Manager — never to `tfvars`, never hardcoded. The application retrieves them at runtime via the AWS SDK. They are never written to any config file or pipeline variable.

### IAM

The EC2 IAM role grants `secretsmanager:GetSecretValue` on the specific secret ARN only — not `secretsmanager:*`, not `*`. The role is attached via an instance profile. No static access keys exist anywhere in the pipeline or on any instance.

### Network isolation

RDS is in a private subnet with no route to the internet gateway. Security groups are applied in addition — not instead. A private subnet provides a structural guarantee that does not degrade with configuration drift. Security groups alone depend on rules being maintained accurately over time.

### Credential scanning — two independent layers

Pre-commit hooks run `detect-secrets`, `tflint`, `checkov`, and `terraform fmt` locally before every commit — preventing secrets from reaching the repository at all. The CI pipeline runs the same scans centrally on every push as a non-bypassable second gate. Pre-commit hooks can be bypassed with `--no-verify`. The pipeline cannot.

The `.secrets.baseline` file is committed to the repository so every developer starts from the same known-safe state and scan behavior is consistent across machines.

## What the pipeline actually does

```
Push to main
  └── Jenkins pipeline triggers
        │
        ├── Build
        │     └── mvn package → produces target/VotingApp.war
        │
        ├── Security scan (runs before any infrastructure is touched)
        │     ├── detect-secrets audit .secrets.baseline
        │     ├── terraform fmt -check -recursive
        │     ├── tflint --chdir=terraform/
        │     └── checkov -d . (fails on HIGH and CRITICAL only)
        │
        ├── Plan
        │     ├── terraform init
        │     ├── terraform plan -input=false -out=tfplan.txt
        │     └── archiveArtifacts tfplan.txt  ← saved for review
        │
        ├── Approval gate  ← human reviews archived plan before apply
        │
        ├── Apply
        │     └── terraform apply -input=false -auto-approve tfplan.txt
        │
        ├── Configure (Ansible)
        │     ├── AWS EC2 dynamic inventory discovers instance IPs
        │     └── ansible-playbook site.yml (common → app_server roles)
        │
        └── Deploy
              └── .war path passed to Ansible at runtime via -e
                  ansible copies VotingApp.war → Tomcat webapps/
```

Security scans run before infrastructure. A failing scan costs nothing — no AWS resources are created. Failing after apply means cleaning up real infrastructure.

Plan and apply are separate stages with a human approval gate between them. The archived plan is what gets applied — not a new plan generated at apply time.

---

## Terraform module structure

```
terraform/
├── modules/
│   ├── vpc/          # VPC, subnets (public/private/db), IGW, NAT Gateway, route tables
│   ├── ec2/          # Launch Template, Auto Scaling Group, IAM role, instance profile
│   ├── rds/          # RDS instance, DB subnet group, parameter group
│   ├── alb/          # Application Load Balancer, target group, listener, health checks
│   └── secrets/      # Secrets Manager secret, CMK, secret version (random_password)
└── main.tf
```

Environment-specific values (CIDRs, AZs, instance types) live in `terraform.tfvars` at the root — not inside modules. Modules accept them as variables and contain no hardcoded environment assumptions. The same module works for dev, staging, and prod by changing only the `tfvars` file.

Each module exposes only the outputs downstream modules need. No module references another module's resources directly — all values flow through the root module.

---

## Ansible roles

```
ansible/
├── roles/
│   ├── common/       # Base dependencies: git, curl, wget, unzip
│   ├── app_server/   # Tomcat, credential injection, .war deployment
│   └── jenkins/      # Jenkins, Java, Terraform, checkov, tflint,
│                     # detect-secrets — all pipeline tools installed here
└── site.yml
```

Ansible connects to EC2 instances using AWS EC2 dynamic inventory — not a static `hosts.ini`. Instance IPs are discovered at runtime via the AWS API using instance tags. This handles the case where Terraform creates instances with IPs that aren't known until apply completes.

Roles are idempotent. Running the playbook twice produces the same result as running it once.

---

## Threat model

| Threat | Control |
|--------|---------|
| Hardcoded credentials in repo | detect-secrets pre-commit + Secrets Manager enforced via IAM |
| Credentials in state file | random_password + encrypted S3 state backend |
| Database reachable from internet | Private subnet + SG restricted to EC2 SG ID only |
| Misconfigured IaC reaching production | checkov gate in CI — HIGH/CRITICAL findings fail the pipeline |
| EC2 accessed directly from internet | Private subnet + ALB as sole ingress point |
| Overprivileged IAM | Role scoped to specific secret ARN; CMK policy as second gate |
| Secret decrypted by wrong principal | CMK resource policy restricts kms:Decrypt independently of IAM |
| Secrets committed to repository | Pre-commit hooks block commit; CI pipeline scans as second gate |
| New instances unreachable by Ansible | Dynamic inventory — IPs discovered at runtime, not hardcoded |

## Local setup

**Prerequisites:** AWS CLI configured, Terraform ≥ 1.x, Ansible, Python 3, Git

```bash
git clone https://github.com/curious-kemi/2-tier-aws-infrastructure
cd 2-tier-aws-infrastructure
cp terraform/terraform.tfvars.example terraform/terraform.tfvars
# edit terraform.tfvars with your values
terraform -chdir=terraform init
terraform -chdir=terraform plan
```

Pre-commit hooks:
```bash
pip install pre-commit detect-secrets
pre-commit install
# verify hooks work
pre-commit run --all-files
```

Ansible collections:
```bash
ansible-galaxy collection install -r ansible/requirements.yml
pip install boto3
```

## Known gaps and future improvements

| Gap | Impact | Planned fix |
|-----|--------|------------|
| Secrets rotation not tested under active connections | Tomcat holds old credentials after rotation | Lambda trigger on rotation event to restart Tomcat |
| ASG deployed but rotation not load-tested | Instance replacement behavior under active traffic unverified | Load test ASG replacement cycle |
| No CloudTrail → alerting pipeline | API activity logged but not monitored | CloudTrail → CloudWatch → SNS |
| No WAF on ALB | Application-layer attacks reach EC2 directly | AWS WAF with managed rule groups |
| MEDIUM checkov findings not blocking | Some valid findings suppressed from pipeline gate | Periodic manual review of MEDIUM findings |

These are scope decisions, not oversights. Documented so the next engineer knows exactly where to start.
